01 / the pain

Three reasons Google keeps rejecting a URI that looks right.

Google's redirect_uri check is an exact string comparison — no wildcards, no normalization. These three things account for almost every mismatch.
P01 · exact match

Scheme, host, port, path, case, and trailing slash must all match.

Google's own docs are explicit: "the http or https scheme, case, and trailing slash must all match." localhost and 127.0.0.1 count as different hosts, and there's no glob syntax like Supabase's redirect allow-list — one differing character is enough to fail.

byte-for-byte
P02 · wrong target

Your code sends a redirect_uri that isn't what your stack should compute.

Supabase and Firebase need their own callback URL in Google Console, not your app's — Google redirects to them first. NextAuth / Auth.js needs a specific /api/auth/callback/google path. Get the stack's own convention wrong and every URI you register is the wrong one.

stack-specific
P03 · client type

A custom scheme or loopback port needs a Desktop / Android / iOS client — never Web.

A "Web application" OAuth client only ever accepts http/https URIs. google-auth-oauthlib, gcloud, Expo without the proxy, and Flutter's native SDK all need a different client type — mixing them up produces this exact error.

03 / how it works

One function. Config in, diagnosis out.

No server, no API key, no signup. doctor-google.js is plain JavaScript — read it, fork it, or run it in your own scripts or CI.
doctor-google.js 0 dependencies 
import { diagnose } from './doctor-google.js';
// or, loaded globally: const { diagnose } = window.GoogleRedirectDoctor;

const result = diagnose({
  error:   { redirectUriFromError, clientType },
  console: { authorizedRedirectUris, authorizedJsOrigins, publishingStatus, savedMinutesAgo },
  app:     { stack, origin, callbackPath, supabaseRef, firebaseAuthDomain,
             expoUsername, expoSlug, useProxy, port, env },
});

Everything runs client-side. The form above calls this exact function in your browser. There is no backend, no API key, and no request that carries your config anywhere.

05 / faq

Questions developers actually search for.

Straight answers to the same redirect_uri_mismatch questions this tool diagnoses — for when you just need the answer, not the checker.
Q01

What does Error 400: redirect_uri_mismatch mean?

Google's OAuth server received a redirect_uri that isn't byte-for-byte identical to one of the Authorized redirect URIs on the OAuth 2.0 Client you're using. Google's docs are explicit: scheme, host, port, case, and trailing slash must all match — no wildcards, unlike Supabase's redirect allow-list. Either your app sends the wrong URI, or the right one isn't registered yet.

Q02

Which redirect URI does NextAuth / Auth.js send to Google?

By default, your origin plus /api/auth/callback/google — e.g. https://myapp.com/api/auth/callback/google — for both NextAuth v4 and Auth.js v5, App Router and Pages Router alike. A custom basePath replaces /api/auth with your own prefix. That exact string, no trailing slash, goes in Google Cloud Console.

Q03

What redirect URI do I put in Google Cloud Console for Supabase?

Supabase's own callback — https://<project-ref>.supabase.co/auth/v1/callback (or your custom Supabase auth domain) — never your app's URL. Google redirects to Supabase first; only then does Supabase redirect on to your app using its own separate Redirect URLs allow-list. Pasting your app's URL here instead is one of the most common causes of this error.

Q04

Why does localhost work but 127.0.0.1 does not (or the other way round)?

Google treats localhost and 127.0.0.1 as two different, unrelated hosts, even though both are loopback — its exact-match rule doesn't normalize them. If your code sends one and you registered the other, you'll see this error even though both point at your own machine. Register the exact host string your code actually sends.

Q05

Why do I still get redirect_uri_mismatch after adding the URI?

Three usual reasons: what you added isn't byte-identical to what your app actually sends (a stray trailing slash, http vs https, www vs apex, or a hidden character from pasting); you edited the wrong OAuth Client ID or the wrong Google Cloud project; or the change hasn't propagated yet — Google's guidance says it can take minutes up to a few hours.

Q06

Can I use a wildcard for Vercel preview deployments?

No. Unlike Supabase's redirect allow-list, Google's Authorized redirect URIs field accepts no wildcards at all — every entry is an exact, literal string. Since each Vercel preview gets its own *.vercel.app URL, none can share one entry. Route the callback through a stable domain even from previews, or register each preview URL individually.
